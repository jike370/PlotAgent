# PlotAgent 产品测试覆盖审计

> 状态：2026-08-21 编辑能力审计基线。
> 范围：34 个正式图类、Agent/工作流、能力目录、Windows UI、Matplotlib、Origin、持久化与导出。
> 目的：解释既有测试为何没有发现 X38 轴范围缺口，并冻结后续测试分层，避免再用某一层全绿代替产品完整性。

## 1. 结论

既有测试没有“失效”，但覆盖边界被误解了：

- 任务状态矩阵证明规划、追问、确认、执行、部分失败、修复、跳过、重新确认、取消、恢复和重启的状态转换与副作用；它不枚举图类编辑参数。
- SEQ-70 证明冻结样例中的 Agent 决策、对象绑定和恢复质量；编辑样例只覆盖少量标题与轴标题，不是 34 图编辑笛卡尔积。
- Windows 黑盒证明实际执行过的 UI 路径；此前主要覆盖创建和代表性编辑，没有逐图逐参数执行。
- 能力目录、编译器和前端都读取同一份 profile。目录漏掉 X38 `bounds` 时三层会“自洽地拒绝”，只有独立产品期望才能发现。
- 双后端共用 T1 视觉适配器，既有适配器测试证明参数可以执行，但没有证明每张图是否正确声明了该参数。

因此，测试必须同时覆盖“生命周期正确”“能力声明完整”“跨层传递正确”“双后端实际执行”四件不同的事。

## 2. 本轮审计发现与处理

| 发现 | 原因 | 处理 |
|---|---|---|
| Y 偏移堆叠线图不能设置 30–90 的 X 轴范围 | profile 漏掉 `set_axis.bounds`，Agent 和 UI 只能据目录拒绝 | X38 开放 `bounds`，新增目录、工作流编译和 UI 提交回归 |
| 双向误差棒图和误差带共用一整套误差参数 | profile 按“误差”粗粒度开放，UI 也同时提交两类参数 | K06 只开放误差棒四参数；K07 只开放误差带四参数；UI 按参数白名单渲染和提交 |
| 产品文档仍声称支持文本标注 | 旧 T1 设计稿未随产品决策收口 | 正式 profile、图形库和聚焦编辑均不开放，用户能力文档删除该项 |
| 混合图无法精确限制某个轴/系列的参数 | `EngineCapability` 目前只有图类级参数，没有目标级参数 | 记录为合同结构缺口；在引入目标级白名单前，不对 X24 等混合语义图盲目扩大能力 |
| Origin 预检把任意 `Origin64.exe` 硬编码成 2024 SR1 | 只做路径探测，没有读取文件版本 | 预检读取 Windows 文件版本；只接受 10.1.0，错误版本或无版本资源的同名文件在启动前返回 `VERSION_UNSUPPORTED` |

## 4. 已有测试真正证明什么

| 测试层 | 证明 | 不能替代 |
|---|---|---|
| Pydantic/Schema | 动作字段类型、范围和序列化稳定 | 某图是否应该开放该动作 |
| 任务状态矩阵 | 状态转换、确认授权、幂等、取消和恢复 | 图类、字段、样式与导出正确性 |
| Profile/Compiler | 声明的角色和参数会被接受或拒绝 | 声明本身是否完整 |
| 共享 T1 适配器 | Matplotlib/Origin 能执行公共参数 | 34 个 profile 是否都声明正确 |
| Profile renderer 测试 | 图形结构、数据绑定和若干专属语义 | 完整编辑参数组合 |
| SEQ-70 | 冻结真实模型样例的规划质量 | UI、Origin 菜单和未入样例的能力 |
| Windows UI 黑盒 | 正式入口中的实际可见行为和产物 | 未执行用例、实现内部不变量 |
| 视觉审查 | 默认态或指定编辑态的外观 | 数据绑定、状态机和恢复 |

## 5. 本轮新增的确定性门禁

1. 固定 34 图共同编辑骨架，禁止 profile 静默丢失标题、轴、系列或导出。
2. 固定轴范围、尺度和反转的完整例外集合；新增图类或修改例外必须显式更新产品期望。
3. 固定 K06/K07 的互斥误差参数集合。
4. 固定“有图例对象才有图例动作”。
5. 固定所有正式图类不开放独立文本标注。
6. 固定 X38 自然语言草稿中的 X 轴 `minimum/maximum` 可以通过工作流编译。
7. 固定前端从生成目录获得 X38 轴范围和 K06/K07 误差白名单，并只提交白名单参数。

这些门禁刻意把期望写在独立测试中，不从同一份生成目录反推期望。

## 6. 仍需分层补齐的产品测试

### P0：发布前必须

- 每个正式图类至少执行一次创建、标题、适用轴范围/尺度、一个适用系列样式、图例或明确无图例、撤销、重做和重启恢复。
- 撤销/重做必须是全量逆向：动作含任一无法从当前 PlotDocument 精确恢复的参数时，产品不得生成部分逆动作或显示可撤销状态。当前发布只承诺基础可逆参数；完整历史版本恢复作为后续架构方案保留。
- 每个公开编辑参数至少在 Matplotlib 和 Origin 各有一个真实原生对象读回；OPJU 用全新 Origin 会话重开。
- Windows UI 对每个“公开/不公开”状态各有正反例，不能只检查按钮存在。
- 导入到绘图覆盖 CSV、多工作表 Excel 和带仪器头的 TXT；类型、单位、来源身份和多源对齐均核对。
- PNG、SVG、OPJU 分别验证成功提示、文件存在、内容非空和可编辑/矢量资格。

### P1：稳定性与兼容

- Provider 超时、限流、断网、代理、无额度、坏 JSON、迟到响应和取消。
- Core/Electron 异常退出、项目锁、执行中重启、部分成功恢复和磁盘写入失败。
- 大数据量、长文本、CJK、缺失值、极值、重复类别、动态系列增删和批量任务。
- 打包产物、全新 Windows 用户、无 Origin/错误 Origin 版本和便携路径。

### P2：合同演进

- 为混合图增加“目标级参数白名单”，覆盖 X24 的三根语义轴、X36 的柱/线系列以及 X39/X40 的 connector/column 对象。
- 将需求—profile—Agent 工具—UI 控件—双后端读回—黑盒证据映射成可生成追踪表，评测只允许引用实际证据。

## 7. 发布判定

发布不能只看单一总通过率。至少同时满足：

1. 任务状态矩阵全绿；
2. 独立能力矩阵全绿；
3. 静态、类型、Schema、Python 与前端测试全绿；
4. 正式 Windows UI 冻结黑盒无产品 FAIL，未执行项明确列出；
5. SEQ-70 达到冻结门槛；
6. Origin 产物在新会话中可重开、可编辑且机械读回一致；
7. 工作树干净，源码、生成合同和用户能力文档来自同一提交。

## 9. 2026-08-21 版本、导出与编辑状态链统一缺口清单

本节是当前施工的唯一功能缺口清单。项目 126 的 OPJU 失败只是审计入口；在本节全部关闭以前，不再按项目或图类零散修复，也不启动新的发布黑盒。

### 9.1 已由正式 UI 或持久化证据确认的缺口

| 能力族 | 已确认现象 | 同类影响范围 | 发布前所需证据 |
|---|---|---|---|
| 当前版本与导出 | 项目 126 界面已显示 S34 v3，但三次 OPJU 暂存请求均携带 v1；Origin 因而按旧轴范围执行并失败 | PNG、SVG、OPJU；所有 34 图；连续编辑、Agent 编辑和聚焦编辑 | 导出前以 Core 最新 PlotDocument 为权威同步当前图；三格式请求和结果均记录同一 plot ID/version；不得静默导出旧版本 |
| 导出成功投影 | Core 返回实际 `plot_version`，但前端导出记录不保存或核对它；只要文件 hash/size 存在就会显示成功 | 三格式成功提示、时间线导出记录、黑盒证据 | 成功记录必须包含请求版本和实际版本，二者不一致时不得报告成功；时间线和测试产物都显示版本 |
| 聚焦编辑撤销/重做 | 标题修改成功生成 v4 后，撤销和重做仍禁用 | 标题、轴、图例等编辑面板表单 | 表单只提交实际变更字段，或历史快照覆盖动作中的全部字段；任何可逆基础编辑成功后立即可撤销，撤销后可重做 |
| 历史参数覆盖 | 编辑面板的标题表单总是附带字体、字号、字重、斜体和颜色，而历史记录器只允许 `text`；轴和图例表单也会附带未纳入逆动作的默认高级参数 | 34 图共同编辑面板 | 对所有公开表单逐项比较“提交参数—当前状态—逆动作”；禁止因未修改的默认值使整条历史失效，禁止部分逆向 |
| 重启后的版本权威 | Core 能恢复每图最新 PlotDocument，但尚无一条产品级确定性测试串联创建、连续编辑、撤销、重做、重启和再次导出 | 所有可编辑图类 | 同一 plot ID 的版本单调增加；重启恢复最后提交版本；三格式导出仍使用恢复后的同一版本 |
| 长表 K01 规划 | 正式 UI 中模型选择长转宽并产生 `series_N` 绑定，但 K01 合同要求 `x/y/group`，最终没有形成可执行计划 | 任务规划、数据操作、自动修复 | 冻结长表夹具；错误草稿必须被校验器拒绝并在受控修复后形成合法 K01 绑定，或直接保留长表的 `x/y/group` |
| 多来源确认依据 | 同一任务项包含多个数据来源时，计划卡顶部数据样本只显示第一个来源，无法核对其余来源与绑定 | 多来源同图、批量、多表任务 | 每个计划步骤显示其全部来源身份；每个绑定可追溯到文件/工作表/列；样本预览不得把首来源冒充全部来源 |
| 部分失败 UI 验收 | Core 和前端组件有部分失败/继续未完成项的确定性测试，但正式 UI 没有稳定故障注入入口，无法可靠制造“成功项保留、仅重试失败项” | 部分成功、修复、跳过、恢复 | 提供仅限测试构建或受控夹具的确定性失败点；同一候选上验证不重复成功项、只执行失败项及重启恢复 |

### 9.2 已确认通过、无需重复修补的相邻行为

- 轴范围的非法输入会在前端阻止提交，项目版本不变。
- 切换项目后，旧项目的迟到 Agent 响应不会覆盖当前项目的计划、错误、图形或对话。
- Core 的 `engine.plots.get` 在省略版本时能够返回指定 plot 的最新版本；`engine.exports.execute` 会严格按 `expected_plot_version` 取文档，不会自行把 v1 替换为最新版本。因此版本同步责任必须在导出前显式完成，不能依赖 Origin 或导出后端猜测。

### 9.3 必须先新增的确定性回归

1. **当前图版本权威：** 创建 v1，连续编辑到 vN，导出前从 Core 同步同一 plot 的最新版本；界面、PNG、SVG、OPJU 请求与导出结果均为 vN。
2. **三格式一致：** 对同一不可变 PlotDocument，三种格式使用同一 plot ID/version/content hash；旧版本请求不得被当作当前导出成功。
3. **完整编辑状态链：** 创建 → 标题 → 适用轴范围/尺度 → 系列样式 → 适用图例 → 撤销 → 重做；每一步生成单调新版本，逆动作完整而非部分回滚。
4. **重启恢复：** 在撤销/重做后关闭并重新打开项目，恢复最终版本，再次导出三种格式时版本不漂移。
5. **34 图能力覆盖：** 对全部 34 个正式 profile 生成标题、轴、系列动作；对 29 个有图例对象的 profile 增加图例动作；矩阵/类别轴和混合图只执行其合同明确允许的范围/尺度。
6. **表单—历史一致：** 聚焦编辑的标题、轴、系列和图例表单只提交用户实际改变且 profile 允许的字段；所有基础可逆动作产生历史项，高级不可精确逆向动作明确不产生伪撤销。
7. **长表与多来源：** 冻结 K01 长表合法规划/错误修复和多来源计划卡完整来源证据。
8. **部分失败：** 不调用真实模型，使用确定性故障注入证明成功项保留、失败项单独重试、跳过、恢复与重启。

### 9.4 统一施工顺序

```text
完成只读审计
  → 冻结本节缺口与失败回归
  → 运行回归并确认当前实现确实失败
  → 按能力族批量修复
  → 全量确定性门禁
  → 集中改前端样式、数据卡和确认卡
  → 暂停并由用户进行视觉验收
  → 定向 Windows UI
  → 冻结干净候选
  → 发布目标 1–9
  → 完整黑盒与 SEQ-70
```

发布目标编号不得与施工步骤混用：发布目标 2 是 `34 × 3 × 3 = 306` 的 PNG/SVG/OPJU 逻辑产物矩阵；发布目标 4 是 34 图的标题、轴、系列、图例、撤销、重做和重启恢复矩阵。

### 9.5 功能批次关闭证据

截至本节对应提交，9.1 的功能缺口已按能力族统一关闭，尚未开始前端视觉改造：

1. 导出前先读取 Core 最新 plot 清单；若清单没有当前对象，则必须按当前 ID/version 精确读取并核对。界面版本落后时先同步最新耐久文档，界面超前、对象缺失或回执 ID/version 不一致时一律停止导出。
2. PNG、SVG、OPJU 的成功回执和对话时间线都记录 `plotVersion`。34 图代表态均执行标题、轴、系列和适用图例编辑，PNG/SVG 产物及 OPJU 请求固定为同一最终版本。
3. 聚焦编辑表单只提交实际变化字段；无变化不创建空版本；右侧/底部图例锚点在公开合同值与界面选项间稳定转换。34 个 profile 的基础历史动作均可生成完整撤销和重做。
4. 34 图持久化回归均执行连续公共编辑、撤销标题、重做标题、关闭项目和重新打开，并核对最终版本、父版本和完整 action 顺序。
5. K01 的 `series_N` 错误绑定由 Core 在确认前按图形角色合同拒绝；Pi 同一 activation 必须提交内容不同的修订草稿后才能继续。
6. 多来源计划卡不再只展示“首项示例”，而是逐来源显示文件/工作表身份、字段角色和前三行样本。
7. 正式桌面部分失败测试使用双重显式开关：`PLOTAGENT_ENABLE_UI_TEST_FAULTS=1` 与 `PLOTAGENT_UI_TEST_FAIL_PROFILE_ONCE=<profile>`。故障只触发一次、发生在提交前、默认完全关闭；用于证明成功项保留和失败项单独修复，不得用于发布运行。

确定性门禁：Python `809 passed`；Vitest `29 files / 259 tests`；Ruff、mypy（184 个源文件）、contracts codegen `--check`、TypeScript typecheck、ESLint 和 production build 全部通过。
